Why money is stored as integers and parsed with Decimal, with an example of a float error

Assistant Response440 words

In financial systems, using standard floating-point numbers (float) is a well-known anti-pattern. In this project, money is handled using a two-part strategy: parsed from text with Decimal and stored/processed as signed int in minor units (paise).

1. The Problem with Floats: IEEE 754 Representation Error

Computers store standard floats in base-2 (binary). Just as $\frac{1}{3}$ cannot be written cleanly in base-10 ($0.3333\dots$), numbers like $0.10$ or $0.70$ cannot be represented cleanly in binary:

>>> 0.1 + 0.2
0.30000000000000004

>>> (0.1 + 0.2) == 0.3
False

Real Financial Errors Caused by Floats

  1. The Truncation Bug (Losing Paise on Conversion):
   # Trying to convert ₹29.99 into paise using float math:
   amount = 29.99
   paise = int(amount * 100)
   print(paise)  
   # Output: 2998  <-- Lost 1 paisa!

Why this happens: 29.99 in IEEE 754 binary float is actually 29.9899999999999984368.... Multiplying by 100 gives 2998.999999999999..., and calling int() truncates the decimals, silently stealing 1 paisa.

  1. Summation Drift Over Thousands of Transactions:
   total = 0.0
   for _ in range(100):
       total += 0.10  # 10 paise

   print(total)         # 9.99999999999998
   print(total == 10.0) # False

Over months of bank statements, small drift errors compound into noticeable discrepancies between account balances and calculated totals.

2. Why Parsed with Decimal

CSV and PDF statements supply numbers as text strings (e.g., "1,23,456.78").

In expenses/money.py:

  • Python's Decimal module works in base-10, matching how humans write currency.
  • Decimal("29.99") * 100 evaluates exactly to Decimal("2999.00"), which converts to int 2999 without rounding or loss.
  • It allows strict validation of decimal places:
  value = Decimal(clean_text)
  if value.as_tuple().exponent < -2:
      raise MoneyParseError("more than 2 decimal places")

This immediately detects and rejects invalid rows like 10.555 rather than silently rounding.

  • Floats are explicitly blocked at the boundary via isinstance(text, str): if a float is passed in, precision might already be compromised before Decimal ever sees it.

3. Why Stored as Integers in Minor Units (Paise)

Once parsed, money is converted to an integer representing paise (e.g., ₹1,234.50 spent is -123450):

  1. Guaranteed Exactness: Integer addition, subtraction, and multiplication in Python and SQLite have arbitrary precision and zero rounding error.
  2. Database Performance & Portability: Storing amount_minor as an SQLite INTEGER column makes queries like SELECT SUM(amount_minor) FROM transactions native, fast, and exact without requiring custom decimal extensions.
  3. Industry Standard: Storing the lowest denomination (minor unit) as an integer is the global standard for banking systems and payment processors (such as Stripe and Razorpay).
  4. Display Separation: Money remains an integer until it is formatted for human eyes via format_inr() (e.g., -123450 $\to$ "-₹1,234.50").

what is anamoly detection

Assistant Response544 words

Anomaly detection (also known as outlier detection) is the process of identifying data points, events, or behaviors that deviate significantly from the expected baseline or normal pattern of a dataset.

1. The Core Idea

Imagine you track your daily coffee spend:

$$\text{₹40, ₹45, ₹40, ₹50, ₹40, ₹45, ₹3,500, ₹40}$$

The ₹3,500 value immediately stands out. It could represent:

  • An error: A typo, accidental duplicate charge, or system glitch.
  • A fraud attempt: Stolen card or unauthorized transaction.
  • A legitimate, unusual event: Buying an entire team lunch or coffee beans in bulk.

Anomaly detection algorithms systematically find these data points without requiring someone to inspect every single record manually.

2. Types of Anomalies

Type Definition Real-World Example
Point Anomaly A single data point that is drastically different from the rest of the dataset. A ₹1,50,000 electronics purchase on a student debit card.
Contextual Anomaly A data point that is normal in general, but anomalous within its specific context (time, location, category). Spending ₹5,000 on electricity in June vs December, or a heavy bench press logged on a scheduled rest day.
Collective Anomaly Individual points look normal, but together as a sequence they indicate abnormal behavior. Fifty ₹10 charges occurring within 30 seconds (card testing attack).

3. Common Approaches to Anomaly Detection

A. Standard Z-Score (Mean & Standard Deviation)

Measures how many standard deviations ($\sigma$) a value ($x$) is away from the mean ($\mu$):

$$Z = \frac{x - \mu}{\sigma}$$

  • Flaw for real-world data: Extreme outliers heavily distort both the mean ($\mu$) and standard deviation ($\sigma$), which causes the standard Z-score to miss subsequent anomalies (masking effect).

B. Robust / Modified Z-Score (Median & MAD)

Instead of mean and standard deviation, it uses the median and Median Absolute Deviation (MAD):

$$M_i = \frac{0.6745 \times (x_i - \text{median})}{\text{MAD}}$$

  • Because the median is not skewed by extreme values, this formula remains accurate even when huge outliers exist.

C. Machine Learning & Proximity-Based Methods

  • Isolation Forest: Builds decision trees; anomalies are isolated closer to the root of the tree because they require fewer splits to separate.
  • Local Outlier Factor (LOF): Measures the local density of a data point relative to its neighbors.
  • Autoencoders (Neural Networks): Trains a network to reconstruct normal data; points with high reconstruction error are flagged as anomalies.

4. How Anomaly Detection Works in This Project

In expenses/anomaly.py, anomaly detection is implemented to alert you when an expense is unusually large for its category:

  1. Per-Category Grouping: It compares a spend only against other transactions in the same category (spending ₹15,000 is normal for Rent, but abnormal for Food & Dining).
  2. Modified Z-Score: Computes the score using exact Decimal math.
  3. MAD = 0 Fallback: If more than half the transactions in a category are identical (e.g. repeated ₹649 Netflix subscriptions), $\text{MAD}$ becomes $0$. The app gracefully falls back to $\text{MeanAD}$ to prevent division by zero.
  4. The Dual-Guardrail Rule:

A debit is only flagged if:

  • $M_i > 3.5$ (statistically unusual), AND
  • $\text{Amount} \ge 2 \times \text{median}$ (materially significant, preventing tiny variances in low-cost items from generating noise).

how does spending forecast work

Assistant Response661 words

Most budget tools only tell you that you've overspent after the month is already over.

The spending forecast system in expenses/forecast.py provides an early warning mid-month (e.g., on day 10 or 15) by projecting where each category will land by the last day of the month, so you can course-correct before it's too late.

1. The Core Problem & Setup

On day $d$ of a month with $D$ days, the engine looks only at transactions that occurred on or before day $d$ (it never peeks into the future).

It projects the month-end total for each category and enforces a baseline rule:

$$\text{Projected Spend} \ge \text{Spent so Far}$$

2. The Four Forecasting Methods

The app implements four distinct projection algorithms:

Method How It Works Formula / Logic Best Used For
pace Linear run-rate scaling. $\text{Spent so far} \times \frac{D}{d}$ Steady, uniform daily spending (e.g., groceries, daily tea/snacks).
last_month Assumes this month will match the previous month. Total spent in that category last month. Predictable regular bills.
smoothing Exponential smoothing over the last 6 months ($\alpha = 0.5$). Weighted average giving the highest weight to recent months. Trending or gradually shifting spend patterns.
typical_rest Spent so far plus your historic median spend for the remainder of the month. $\text{Spent so far} + \text{median}(\text{spend after day } d \text{ in last 6 months})$ Front-loaded expenses (rent, tuition fees, monthly utility bills).
Note:
Why pace alone fails: If you pay ₹25,000 rent on day 3 of a 30-day month, naive pace projects:
$$₹25,000 \times \frac{30}{3} = ₹2,50,000$$
It falsely predicts a 10× catastrophe! In contrast, typical_rest looks at previous months, sees that spending after day 3 in the Rent category is usually ₹0, and projects an accurate ₹25,000.

3. Automatic Method Selection (Backtesting with WAPE)

Instead of forcing you to guess which mathematical formula to use, the system tests all four methods against your own past transaction history:

  1. It takes past complete months (requiring $\ge 3$ prior months of history).
  2. It simulates standing at checkpoints: Day 7, Day 14, and Day 21.
  3. It generates a projection using each of the 4 methods and compares it to what actually happened at the end of that month.
  4. It scores each method using WAPE (Weighted Absolute Percentage Error):

$$\text{WAPE} = \frac{\sum |\text{Projected} - \text{Actual}|}{\sum \text{Actual}}$$

(WAPE is used instead of MAPE because standard MAPE explodes when spending is small — e.g. predicting ₹50 on an actual ₹10 spend is a 400% error, whereas WAPE weights errors by money).

The algorithm with the lowest historical WAPE on your data is automatically chosen.

(On test benchmarks, typical_rest scored an error of ~28.8%, compared to pace which suffered 75.7% error).

4. Budget Early Warning & "Safe to Spend"

For each category with a configured budget:

  1. Status Badges:
  • over: Already exceeded the monthly budget limit.
  • at_risk: Currently within budget, but projected month-end total will breach the limit.
  • on_track: Projected to finish safely within budget.
  1. Safe to Spend Per Day:

$$\text{Safe per day} = \frac{\max(0, \text{Budget} - \text{Spent so far})}{\text{Days left in month}}$$

  1. Actionable Alerts: Formats natural-language warnings such as:
"At this pace Groceries will reach ₹11,821 — 48% over its ₹8,000 budget."

5. Historic Replay Mode

On the UI page (ui/forecast_page.py):

  • For the current month, it uses today's date.
  • For past months, it acts as a "time machine" (e.g., "Pretend today is 15 September 2026"). It draws a chart showing:
  • Solid line: Actual spend up to that day.
  • Dashed line: What the model projected to the end of the month.
  • Muted line: What actually ended up happening, allowing you to see exactly where unexpected one-off purchases (like a sudden laptop repair) diverted from the forecast.

what are desicion logs

Assistant Response480 words

A Decision Log (often called an Architecture Decision Record or ADR in professional software engineering) is a formal, chronological record of significant technical and product choices made during a project.

It documents not just what was decided, but more importantly why that choice was made over alternatives, including the trade-offs and constraints involved.

1. What Goes into a Decision Log?

Typically, each entry records three things:

  1. Date: When the decision was agreed upon.
  2. Decision: What was changed, implemented, or chosen.
  3. Rationale / Trade-off: Why that option was selected, what edge case forced the decision, or what alternatives were rejected.

2. Why Decision Logs are Essential

  • Prevents "Why did we do this?" Amnesia: Months later (or during a viva / code review), developers often forget why a non-obvious piece of code was written. A decision log prevents someone from "cleaning up" code that was actually solving a subtle edge case.
  • Documents Trade-offs: Engineering rarely has perfect solutions, only trade-offs (e.g., speed vs. memory, strict privacy vs. external API convenience).
  • Formalizes Rule Exceptions: If a core project rule must be bent (e.g. allowing one specific network call in a strict offline-only app), the decision log records the explicit owner approval and safety boundaries.

3. Concrete Examples from This Project's Decisions Log

In this repository, the Decisions Log is kept in SPEC.md Section 16. Here are notable examples from the project:

1. Preventing Substring Bugs (Cash vs. Treatment)

  • Decision: Cash categorization rules match ATM WDL, ATM CASH, and CASH WDL — never just plain ATM.
  • Reason: The word ATM is a substring of TREATMENT. Matching plain ATM silently converted hospital and medical bills into "Cash" expenses.

2. The Anomaly Detection 2× Guardrail

  • Decision: Only flag an anomaly if the modified z-score $M > 3.5$ and the amount is at least $2 \times$ the category median.
  • Reason: When fixed-price subscriptions dominate a category (e.g. 14 out of 29 Entertainment transactions were ₹649), the $\text{MAD}$ became just ₹0.69. Consequently, ordinary ₹300 cinema tickets triggered statistical anomaly alarms. The $2\times$ materiality rule fixed this noise.

3. Exception to the "No Network" Privacy Rule (Q5)

  • Decision: Fetch live European Central Bank (ECB) rates for foreign currency conversion.
  • Reason: The project rule strictly forbade network calls. The decision log formally recorded an amendment: only currency code and date are sent (no amounts, descriptions, or user data), and all fetched rates are cached in SQLite so subsequent runs work completely offline.

4. The light-dark() Theme Switch Fix

  • Decision: Use CSS light-dark() variables rather than choosing colors in Python.
  • Reason: Streamlit has an upstream limitation where toggling the theme in the top-right ⋮ menu does not rerun the Python script. Python could not react to theme changes, so only client-side CSS could switch colors instantly.

what can be the other possible viva questions?

Assistant Response1021 words

Here is a curated list of the most probable Viva Questions for this project, organized by topic, along with the key points examiners look for.

Category 1: Machine Learning & NLP (expenses/learn.py)

Q1: "Why did you choose Complement Naive Bayes over Logistic Regression or SVM?"

  • Answer: Real bank transaction data has severe class imbalance (e.g. hundreds of Food & UPI debits vs. only 1–2 Salary credits). Standard Multinomial Naive Bayes tends to favor classes with more training examples. Complement Naive Bayes (CNB) calculates weights using statistics from the complement of each class, making it significantly more accurate and robust on unbalanced text datasets. In benchmark tests, it matched or beat Logistic Regression while training in under a second on CPU.

Q2: "Why use a Merchant-Grouped Train/Test Split instead of standard train_test_split?"

  • Answer: (Examiners love this!) A random split would put SWIGGY in both training and test sets. The model would just memorize the name and boast a fake 99% accuracy. A merchant-grouped split ensures that no merchant appears in both train and test sets. This measures what truly matters: can the model categorize a brand-new merchant it has never seen before?

Q3: "Why include Character 3–5 n-grams alongside Word 1–2 n-grams in TF-IDF?"

  • Answer: Indian bank narrations often truncate or mangle merchant names (e.g., SWIGGY*BANGALORE, SWGY01, AMZN-PAY). Word n-grams would treat them as separate, unknown words. Character n-grams catch internal sub-words (SWIG, AMZN), enabling the model to recognize abbreviations and typos.

Q4: "Why is the model forbidden from training on its own predictions (category_source = 'model')?"

  • Answer: To prevent a destructive feedback loop (bias amplification). If the model makes a wrong guess (e.g., misclassifying a hospital bill as Shopping) and then trains on that guess, it becomes increasingly confident in its own mistake over time. It only trains on human manual overrides (weight 3) and verified rules (weight 1).

Category 2: Ingestion & Data Engineering (expenses/columns.py, combine.py)

Q5: "How do you detect column roles in bank statements that have NO header row?"

  • Answer: We use statistical inspection of cell contents:
  • A column where $\ge 90\%$ of cells parse as dates is the Date column.
  • A column where $\ge 90\%$ of cells are numeric and $\ge 80\%$ have two decimals is Money (the two-decimal rule ensures cheque numbers like 001234 are ignored).
  • To tell Debit from Credit, we check arithmetic against the running balance:

$$\text{Balance}_{\text{current}} - \text{Balance}_{\text{previous}} = \text{Credit} - \text{Debit}$$

The arrangement that satisfies this equation across $\ge 80\%$ of rows proves the orientation mathematically.

Q6: "How do you handle internal transfers between your own accounts?"

  • Answer: If you transfer ₹10,000 from HDFC to SBI, simple importing would log ₹10,000 expense and ₹10,000 income, distorting your true savings. The combined importer detects pairs: one debit and one credit with the exact same amount, in different accounts, occurring within $\pm 3$ days of each other. It flags them as Transfers, excluding them from both income and expense totals.

Q7: "How does fingerprinting handle two genuine identical purchases on the same day?"

  • Answer: The SHA-256 fingerprint includes an occurrence index:

$$\text{sha256}(\text{account} \mid \text{date} \mid \text{amount} \mid \text{description} \mid \mathbf{occurrence})$$

If you buy two ₹20 teas on the same day, the first gets occurrence = 0 and the second gets occurrence = 1. Both produce unique hashes and are saved. If you re-import the file, both hashes match existing rows and are correctly skipped as duplicates.

Category 3: Statistics & Forecasting (expenses/anomaly.py, forecast.py)

Q8: "Why use Modified Z-score instead of standard Z-score for anomalies?"

  • Answer: Standard Z-score uses mean ($\mu$) and standard deviation ($\sigma$). If you make one massive ₹2,00,000 purchase, it artificially inflates the mean and blows up the standard deviation, causing the algorithm to miss subsequent anomalies (the masking effect). The Modified Z-score uses the median and MAD (Median Absolute Deviation), which are resistant to extreme outliers.

Q9: "Why does the forecast use WAPE instead of MAPE?"

  • Answer: MAPE (Mean Absolute Percentage Error) divides by actual spend. For small categories (e.g., ₹10 spent on parking, but projected ₹50), MAPE computes a $(50 - 10)/10 = 400\%$ error, skewing the overall score. WAPE (Weighted Absolute Percentage Error) divides the sum of absolute errors by the total money spent:

$$\text{WAPE} = \frac{\sum |\text{Projected} - \text{Actual}|}{\sum \text{Actual}}$$

This weights errors proportionally to the amount of money involved.

Q10: "Why does the simple 'pace' forecast fail on rent or utility bills?"

  • Answer: Naive pace multiplies daily spend by total month days ($\text{spent} \times D / d$). If you pay ₹20,000 rent on Day 2, pace calculates:

$$₹20,000 \times \frac{30}{2} = ₹3,00,000$$

The project implements typical_rest, which takes spend-to-date and adds the historical median of what is normally spent after that day, recognizing that post-rent spend is close to zero.

Category 4: Security, Systems & Database

Q11: "How are bank PDF passwords stored securely?"

  • Answer: They are encrypted at rest using Fernet (AES-128-CBC + HMAC-SHA256) via the cryptography library. Crucially, the encryption key is stored in a separate, owner-restricted file (pdf-passwords.key) outside the database. If an attacker copies expenses.db, they cannot decrypt the passwords without the companion key file.

Q12: "Why does the Docker container listen on 0.0.0.0 internally, while docker-compose.yml binds to 127.0.0.1?"

  • Answer: Inside a container, 127.0.0.1 refers only to the container itself; if the app bound to 127.0.0.1 internally, Docker could not forward traffic from the host. Therefore, the app listens on 0.0.0.0 inside its network namespace. On the host side, Docker Compose binds specifically to 127.0.0.1:8501:8501 to ensure the port is accessible only to the local machine, preventing anyone on the same Wi-Fi network from accessing your financial data.

Q13: "Why is the passphrase hashed with PBKDF2 instead of standard MD5 or SHA-256?"

  • Answer: Plain hashes like MD5 and SHA-256 are designed to be fast, making them vulnerable to brute-force and rainbow table attacks. We use PBKDF2-HMAC-SHA256 with 600,000 iterations and a random salt, forcing significant CPU work per attempt and making brute-force cracking practically impossible.
